# 交付与截止时间协议（Checkpoint V1 保底）

目标不是在截止前生成理论最优的局部内容，而是在截止时间前**可靠产出并成功提交**当前条件下质量最高且合规的成果。二者冲突时，可提交性优先于局部完美。本协议不改变 92 分放行线的语义：`submission_ready` 仍只在完整门禁通过后标记；Checkpoint 是"人在环上、可立即人工提交"的物理保底，不是质量认证。

## 一、时间与提交约束核验

1. Stage 0 读取系统时间、时区与剩余时间，从当届官网核验截止时间、时区、允许格式、数量、大小、命名与上传入口；往届日期只作检索线索。
2. 记录三个时间点并写入状态：`官方截止时间`、`内部内容冻结时间`、`最迟安全导出时间`。内部时间必须为异常处理、重导出和人工上传留出显著缓冲。
3. 无法核验官方时间时标记未知并请用户确认；不得把推测写成事实。

## 二、尽早走通完整链路

主要内容未完成时，先用最小真实样例走通一次：

`代码 → 结果表/图 → 论文源文件 → DOCX/PDF → 支撑材料 → 压缩包 → 人工打开检查`

格式转换、字体公式渲染、压缩、上传都是正式任务，不是零成本收尾。Agent 不能代替用户登录、上传或最终确认时，必须给出待办清单并明确提醒。

## 三、Checkpoint 状态机

为每个已通过状态保留独立快照（`PROJECT_ROOT/checkpoints/`），记录文件清单与 SHA-256：

1. **Checkpoint V1**：首次完整、可打开、满足已核验硬约束（页数、无目录、非图片 PDF、匿名、命名）且包含全部必需文件的可提交版本。**优先尽早产出，不等所有优化完成**——目标在内部内容冻结时间前留有余量地获得 V1。
2. **Checkpoint V2**：在不破坏 V1 的前提下受控优化（如扩写正文向 29–30 页目标靠拢、补充图表），完成后重跑受影响门禁。
3. **内容冻结**：停止改动正文、数据、图表和引用，只允许修复阻止提交的确定性问题。
4. **最终导出**：从冻结内容生成正式 PDF 与支撑材料包，运行完整 `validate_submission.py`。
5. **完整性与合规检查**：可打开、可解压、命名、格式、大小（双文件各 ≤20MB、论文不压缩）、页数（正文 ≤30 页；附录全国不限、赛区建议 ≤20 页；全文 ≤51 页为赛区口径）与官方要求逐项核对；确认电子版无承诺书/编号专用页。
6. **人工上传与确认**：提醒用户预留登录、网络、平台校验和凭证留存时间；未经平台证据确认不得声称已提交。

V1 出现后任务**不得回到没有任何可提交版本的状态**；后续修改在副本上进行，已验证的 V1 不得被原地覆盖。92 分门禁未通过但时间逼近冻结线时，向用户明确报告：当前 panel 分数、未解决问题、V1/V2 状态与剩余风险，由用户决定提交哪个版本——Skill 不得自行决定降标提交，也不得为凑 92 分让用户错过上传窗口。

## 四、按异常而非最快耗时预留缓冲

对格式转换、复杂排版、网络上传和长任务，按"发生一次异常并完成排查、重试后仍能提交"安排缓冲。剩余时间不足以覆盖失败与回滚成本时，缩小修改范围，优先保护当前可提交版本。

临近内容冻结或最迟安全导出时间，每次准备新修改前先问：

> 如果这次修改失败、耗时远超预期或工具异常，我手里的版本还能否按时提交？

答案是否定的，默认不执行该修改；保留当前可提交版本，只处理直接阻止合规提交的问题。

## 五、提交前最低检查

- 官方截止时间、时区、提交入口已核验。
- 最新 Checkpoint 仍可独立打开；V2/最终版失败时可立即回退 V1。
- PDF 已实际打开抽检公式、图表、分页、字体和参考文献；确认非图片 PDF（文本可复制）、无目录、电子版第一页为摘要专用页（无承诺书/编号页）、正文 ≤30 页且全文符合赛区口径 ≤51 页。
- Word 无残留 Markdown 标记：`**`、反引号、`#`、表格竖线、`$`/`$$`、`[待补充]`。
- 压缩包已实际解压验证，清单、命名、大小符合当届规则。
- 已明确提醒用户完成登录、上传、平台校验、最终提交与凭证留存。
